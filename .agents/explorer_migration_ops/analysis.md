## 1. الملخص التنفيذي والملاحظات الجوهرية (Executive Technical Summary)

- **بروتوكول الهجرة الثلاثي (3-File Protocol) [مؤكد]**: مجلد `MIGRATION/` غير موجود حالياً في جذر المشروع (`d:\elctercity`). يتطلب معيار المشروع الصارم وجود **ثلاثة ملفات حصرية** داخله دون أي ملف رابع:
  1. `MIGRATION/MASTER_PLAN.md` (المخطط المعماري الشامل، سجل القواعد المحاسبية، وتفصيل المراحل).
  2. `MIGRATION/EXECUTION_LOG.md` (سجل التنفيذ اللحظي ذو بوابات العبور الصارمة Phase Gates مع إثباتات المخرجات وسجلات النجاح).
  3. `MIGRATION/FINAL_AUDIT.md` (المراجعة والتدقيق المستقل الذي ينتهي بحكم حاسم صريح: `READY` أو `NOT_READY`).
- **حالة تطبيق المحمول (Mobile App Deprecation) [مؤكد]**: تم التحقق الميداني من أن مجلد `mobile_app/` وأي حزم `*.apk` (مثل `SmartPowerCollector_v2.apk`) قد تم حذفها مادياً من القرص بالفعل في عمليات تنظيف سابقة. لا توجد أي اعتمادات برمجية متبقية في الباك إند أو الفرونت إند تعتمد على وجود تطبيق الهاتف، وتقتصر الإشارات المتبقية على سطور مهملة في `.gitignore` وملاحظات توثيقية تاريخية، مع وجود خيار تجاوب واجهة المتصفح فقط (`isMobileMode`) داخل React.
- **خطة التعافي من الكوارث والتحصين (Disaster Recovery & Hardening) [مؤكد]**:
  - يتطلب النظام جدولة نسخ احتياطي يومي آلي لقاعدة بيانات PostgreSQL المحلية (`smartpower_db`) باستخدام أداة `pg_dump` بصيغة Custom Format (`-Fc`).
  - رصد ذكي لمنافذ الفلاش ميموري (USB Mirroring) على نظام ويندوز عبر استدعاءات Win32 API (`DRIVE_REMOVABLE = 2`) مع نسخ تلقائي للملفات ومطابقة التجزئة (SHA-256)، والتراجع الآمن مع إشعار تحذيري في حال عدم وجود الفلاش.
  - توفير فحص ذاتي عند الإقلاع البارد (Cold-Boot Health Check) وإعادة ضبط العمليات المعلقة (Crash Recovery) لإقلاع الخادم `server.exe` في زمن يقل عن 0.1 ثانية.
- **منظومة الإكسل (Excel Import/Export Architecture) [مؤكد]**:
  - تصدير الكشوفات (`الكشف العام` و `كشف الدورة`) يتطلب تطبيق الـ RTL الكامل والتنسيق اللوني للخلايا.
  - استيراد المشتركين يتطلب دعم القراءة التتابعية السريعة (Streaming) وقاموس مطابقة مرن للمسميات العربية ومعالجة غير متزامنة (Async Jobs) وتفادي تشبع الذاكرة عبر حزمة `github.com/xuri/excelize/v2` في Go.

## 2. المسح التفصيلي لبروتوكول الهجرة (3-File Migration Protocol)

### أ. الوضع الراهن للمجلد `MIGRATION/`
- الفحص الميداني أكد عدم وجود المجلد `d:\elctercity\MIGRATION`.
- **الخطر المعماري**: إنشاء ملفات عشوائية أو تقارير متفرقة داخل `MIGRATION/` يعد مخالفة صريحة لشروط القبول (Acceptance Criteria) التي تنص على: *"Exactly three files exist in MIGRATION/: MASTER_PLAN.md, EXECUTION_LOG.md, FINAL_AUDIT.md"*.
- **الإجراء المطلوب**: إنشاء المجلد وحصر كافة وثائق الهجرة بدقة متناهية داخل هذه الملفات الثلاثة فقط.

### ب. المتطلبات الهندسية لملف `MIGRATION/MASTER_PLAN.md`
يجب أن يشمل الملف المكونات البنيوية التالية:
1. **فهم النظام الراهن (Current System Baseline)**:
   - تحليل مكونات الباك إند القديم (Node.js/Express + Prisma ORM + Baileys WhatsApp + Puppeteer).
   - توثيق المشاكل الحالية: بطء التشغيل، استهلاك ذاكرة يتجاوز 250MB، الاعتماد على خدمات سحابية ومحركات ثقيلة لتصوير الفواتير.
2. **سجل القواعد المحاسبية والمالية (Business Logic Inventory)**:
   - معادلة الاستهلاك: `الاستهلاك = القراءة الحالية - القراءة السابقة`.
   - احتساب تكلفة الوحدات المفقودة: `تكلفة الفاقد = الوحدات المفقودة * سعر الكيلوواط`.
   - إجمالي الفاتورة: `قيمة الاستهلاك + الرسوم الثابتة + تكلفة الفاقد + المتأخرات`.
   - حواجز العداد غير التنازلية (Non-monotonic Reading Guards): منع تسجيل أي قراءة تقل عن القراءة السابقة على مستوى قيود قاعدة البيانات (`CHECK (current_reading >= previous_reading)`).
   - آلية التوزيع المائي للدفعات (FIFO Waterfall Payment Allocation): سداد الفواتير القديمة أولاً بأول، وتوزيع الدفعات بدقة على (المتأخرات -> الرسوم -> الاستهلاك) وحفظ الفائض في جدول `customer_credits`.
   - إعادة الحساب التراجعي التتابعي (Billing Cycle Retroactive Recalculation): عند تعديل قراءة أو دفعة سابقة، يتم تحديث كافة الأرصدة والمتأخرات في الدورات اللاحقة آلياً وبشكل متسلسل.
   - الترقيم المركب للفاتورة: الصيغة المعتمدة الحتمية `INV-[Cycle]-[SubscriberNumber]`.
3. **المعمارية المستهدفة (Target Architecture)**:
   - خادم Go مستقل مجمّع في ملف تنفيذي واحد `server.exe` بحجم < 25MB، مدمج به الواجهة الأمامية عبر `//go:embed dist/*`.
   - استهلاك RAM أقل من 35MB وسرعة إقلاع < 0.1 ثانية.
   - قاعدة بيانات PostgreSQL محلية على المنفذ 5432 باسم `smartpower_db`.
   - محرك WhatsApp نقي بدون CGO عبر `whatsmeow` مع تخزين الجلسات مباشرة في PostgreSQL.
   - محرك تصوير فواتير A5 خفيف عبر `chromedp` مستفيداً من متصفح Edge المدمج في ويندوز.
4. **استراتيجية الهجرة المرحلية (Phased Migration Strategy)**:
   - المرحلة 1: تهيئة قاعدة بيانات PostgreSQL وإنشاء المخطط المتين والقيود المحاسبية.
   - المرحلة 2: بناء محرك الحسابات المالية ونماذج البيانات في Go.
   - المرحلة 3: بناء مسارات الـ REST API المتطابقة 100% مع عقد `API_CONTRACT.md`.
   - المرحلة 4: تكامل محرك `whatsmeow` وطابور الرسائل المحلي المجدول (بفارق 8-15 ثانية).
   - المرحلة 5: محرك الإكسل `excelize` ومحرك الفواتير A5 ذو الوصلين.
   - المرحلة 6: بناء الفرونت إند ودمجه كملف تنفيذي واحد `server.exe`.
   - المرحلة 7: فحص التعافي من الكوارث، اختبارات الإجهاد، وإجراء التدقيق الختامي.

### ج. المتطلبات الهندسية لملف `MIGRATION/EXECUTION_LOG.md`
1. **سجل تشغيلي حي وتصاعدي**: لا يتم ملؤه دفعة واحدة مسبقاً، بل يُسجل فيه كل إجراء لحظة بلحظة.
2. **بوابات العبور المبنية على الأدلة (Evidence-Based Phase Gates)**:
   - لكل مرحلة: (الوصف الفني، الأمر المنفذ، المخرجات الفعلية من الطرفية Verbatim Outputs، المسارات وأرقام السطور، وحالة البوابة `PASS` أو `FAIL`).
   - يُمنع الانتقال للمرحلة اللاحقة قبل توثيق نجاح المرحلة الحالية والحصول على راية `PASS`.

### د. المتطلبات الهندسية لملف `MIGRATION/FINAL_AUDIT.md`
1. فحص شامل ومستقل لكافة المعايير (حجم الملف التنفيذي، زمن الإقلاع، انعدام أخطاء التقريب المالي، سلامة قيود العدادات، طباعة الفاتورة A5 بالأرقام الإنجليزية، عمل الواتساب، والنسخ الاحتياطي).
2. يجب أن ينتهي التقرير حصراً بقرار نهائي حاسم وكبير: `READY` أو `NOT_READY`.

## 4. خطة التعافي من الكوارث والتحصين (Disaster Recovery & Hardening)

### أ. أتمتة النسخ الاحتياطي لقاعدة بيانات PostgreSQL (`pg_dump`)
1. **صيغة النسخ المعتمدة**:
   - استخدام صيغة PostgreSQL المخصصة:
     ```bash
     pg_dump -h localhost -p 5432 -U postgres -d smartpower_db -Fc -f "backups/smartpower_db_YYYYMMDD_HHMMSS.dump"
     ```
   - مميزات الصيغة `-Fc` (Custom Format):
     - ضغط تلقائي عالي يقلل حجم النسخة بنسبة تصل إلى 80%.
     - دعم الاسترجاع الانتقائي للجداول والفهارس عبر `pg_restore`.
     - حماية تامة من تشويه البيانات النصية والترميز العربي (UTF-8).
2. **جدولة النسخ الآلي**:
   - في خادم Go، يتم تشغيل `goroutine` مع `time.Ticker` يعمل كل 24 ساعة (مثلاً في تمام الساعة 02:00 صباحاً)، أو عند إغلاق/تشغيل البرنامج إذا فاتت الدورة.
   - الاحتفاظ بنسخ احتياطية لمدة 30 يوماً في المجلد المحلي `%LOCALAPPDATA%\SmartPower\backups` مع حذف النسخ الأقدم تلقائياً لمنع امتلاء القرص الصلب.

### ب. رصد ومطابقة الفلاش ميموري (USB Mirroring & Fallback)
1. **خوارزمية الكشف عن أقراص الـ USB في Go على Windows**:
   - استدعاء دالة Win32 API الرسمية: `GetDriveTypeW(drivePath)`.
   - تحديد القرص كـ USB إذا كان نوعه مساوياً لـ `DRIVE_REMOVABLE` (القيمة الرقمية 2):
     ```go
     // فحص الأقراص من D: إلى Z:
     for d := 'D'; d <= 'Z'; d++ {
         drive := fmt.Sprintf("%c:\\", d)
         driveType := windows.GetDriveType(windows.StringToUTF16Ptr(drive))
         if driveType == windows.DRIVE_REMOVABLE {
             // تم اكتشاف فلاش ميموري متصل
         }
     }
     ```
2. **آلية النسخ والمطابقة**:
   - إنشاء المجلد الخارجي: `<USB_DRIVE>:\SmartPower_Backups\`.
   - نسخ ملف الـ `.dump` وملف البيان `manifest.json`.
   - احتساب تجزئة SHA-256 للنسخة المحلية ومطابقتها فورياً مع النسخة المنسوخة على الفلاش ميموري للتحقق من سلامتها بنسبة 100%.
3. **آلية التراجع الآمن في حال غياب الـ USB (Fallback Mode)**:
   - في حال عدم توصيل فلاش ميموري، يكتمل النسخ الاحتياطي المحلي بنجاح، ويتم تسجيل الحالة:
     `{ local_backup: "PASS", usb_mirror: "NOT_CONNECTED" }`.
   - لا يتعطل الخادم ولا يتوقف النظام، بل يظهر تنبيه لطيف في شريط الحالة:
     *"النسخ الاحتياطي المحلي ناجح. تنبيه: يرجى إدخال فلاش ميموري USB لحفظ نسخة خارجية وضمان الحماية من تلف الجهاز"*.

### ج. الفحص الصحي عند الإقلاع والتعافي من الانهيار (Cold-Boot & Crash Recovery)
1. **خطوات الإقلاع البارد (Cold-Boot Sequence) لملف `server.exe`**:
   - **الخطوة 1**: فحص المتغيرات وبيئة التشغيل المحلية والاتصال بـ PostgreSQL على المنفذ 5432 عبر استعلام `SELECT 1;`.
   - **الخطوة 2**: في حال فشل الاتصال، فحص خدمة الويندوز `postgresql-x64-16` وعرض رسالة خطأ واضحة باللغة العربية.
   - **الخطوة 3**: تشغيل التهيئة التلقائية (GORM AutoMigrate) والتأكد من وجود كافة الجداول والقيود المحاسبية.
   - **الخطوة 4 (Crash Recovery)**:
     - فحص جدول طابور الواتساب `whatsapp_queue_messages` وإعادة تعيين أي رسائل عالقة بحالة `SENDING` إلى `PENDING` لضمان عدم ضياعها أو تجميدها بعد انهيار النظام أو انقطاع التيار الكهربائي.
     - معالجة أي مهام استيراد غير مكتملة في `import_jobs`.
   - **الخطوة 5**: تشغيل عمال الخلفية (طابور الواتساب ومجدول النسخ الاحتياطي).
   - **الخطوة 6**: بدء استماع خادم Go Fiber على المنفذ 3000 وتقديم واجهة React المدمجة في أقل من 0.05 ثانية.

## 5. منظومة استيراد وتصدير الإكسل عبر Go `excelize`

### أ. فحص وتحليل الوضع الحالي (Node.js & React)
1. **التصدير من الباك إند (`excel-export.service.ts`)**:
   - مسار `GET /api/export/general-roster`: توليد ورقة `الكشف العام` (7 أعمدة: رقم المشترك، الاسم، العنوان، رقم العداد، خط السير، القراءة السابقة، القراءة الحالية فارغة للمحصل) مع اتجاه RTL ورأس أزرق (`#4F81BD`).
   - مسار `GET /api/export/billing-cycle/:cycleId`: توليد ورقة `كشف الدورة` (17 عموداً مفصلاً تشمل الاستهلاك، السعر، الرسوم، المتأخرات، الإجمالي، المدفوع، المتبقي) مع اتجاه RTL ورأس أخضر (`#00B050`).
2. **التصدير من الواجهة الأمامية**:
   - في `ReportsHub.tsx` و `ExcelGrid.tsx` و `UnreadMeters.tsx`: يتم استخدام تصدير CSV متوافق مع الإكسل بإضافة بادئة UTF-8 BOM (`\uFEFF`) لضمان ظهور الأحرف العربية بدون تشويه.
   - في `ArrearsReport.tsx`: يتم استخدام مكتبة `xlsx` (SheetJS) محلياً في المتصفح.
3. **الاستيراد من الباك إند (`excel-import.service.ts` و `excel-async-import.service.ts`)**:
   - دعم قاموس مطابقة واسع للعناوين العربية (مثل: `رقم المشترك / رقم الحساب / كود المشترك`، `المتاخرات / الرصيد المتبقي`، `الجوال / تلفون`).
   - دعم المهام غير المتزامنة (Async Jobs) مع تجزئة SHA-256 للملف لمنع تكرار المعالجة ونبضات دورية (Heartbeat) وتتبع نسب الإنجاز وسجلات الأخطاء.

### ب. التصميم المستهدف باستخدام مكتبة Go `excelize/v2`
1. **كفاءة الذاكرة والأداء (Streaming Capabilities)**:
   - استخدام `f.NewStreamWriter(sheetName)` عند تصدير آلاف الصفوف، مما يقلل استهلاك الذاكرة لأقل من 15MB مقابل مئات الميجابايت في Node.js.
   - استخدام `rows, err := f.Rows(sheetName)` لقراءة الملفات الضخمة صفاّ بصف (Iterator pattern) وتجنب تحميل كامل المستند في الذاكرة.
2. **تطبيق تنسيق RTL والألوان في Go**:
   ```go
   // ضبط ورقة العمل باللغة العربية من اليمين لليسار
   isRTL := true
   _ = f.SetSheetView(sheetName, 0, &excelize.ViewOptions{
       RightToLeft: &isRTL,
   })
   
   // إنشاء نمط ترويسة الجدول بالألوان والخط العريض
   headerStyle, _ := f.NewStyle(&excelize.Style{
       Font: &excelize.Font{Bold: true, Color: "#FFFFFF", Size: 11},
       Fill: excelize.Fill{Type: "pattern", Color: []string{"#00B050"}, Pattern: 1},
       Alignment: &excelize.Alignment{Horizontal: "center", Vertical: "center"},
   })
   ```
3. **قاموس المطابقة الذكي للعناوين في Go**:
   - إنشاء مصفوفة قواميس للمفردات العربية والإنجليزية للتعرف التلقائي على الأعمدة بغض النظر عن اختلاف تسميات الموظفين لملفات الإكسل.
   - تنظيف أرقام الهواتف وفرض الصيغة اليمنية (`+967 7...`).
   - استخدام العمليات المجمعة في قاعدة البيانات `gorm.CreateInBatches(records, 500)` لتسريع الاستيراد وتفادي القيود الزمنية للاتصال.
