- **المنهجية**: 25 خيط عمل متزامن يحاولون تسجيل أرقام مشتركة تتطابق بعد إزالة الأصفار ولكن تختلف في عدد الأصفار البادئة (`7752951`, `07752951`, `007752951`, `0007752951`, `00007752951`).

  - نظراً لأن جميع الطلبات وصلت في نفس الميلي ثانية، رأت جميع الخيوط أن المشترك غير موجود.

- **الحكم**: **FAIL / VULNERABILITY CONFIRMED** — ثغرة سباق زمني تتطلب تحديث الفهرس في PostgreSQL ليتضمن `REGEXP_REPLACE(TRIM(LOWER(subscriber_number)), '^0+', '')`.
- **الإجراء المتخذ**: تم تنظيف وحذف سجلات الفحص التجريبية فورياً لإعادة قاعدة البيانات لحالتها النقية.

## 5. التوصيات الفنية القاطعة (Actionable Recommendations)

1. **إصلاح فهرس المشترك في PostgreSQL فوراً (P0)**:
   تنفيذ أمر استبدال الفهرس على قاعدة البيانات الحية لفرض المعايرة بالأصفار على مستوى محرك البيانات:
   ```sql
   DROP INDEX IF EXISTS uq_customers_subscriber_number_clean;
   CREATE UNIQUE INDEX uq_customers_subscriber_number_clean 
   ON public.customers USING btree (REGEXP_REPLACE(TRIM(BOTH FROM lower(subscriber_number)), '^0+', '')) 
   WHERE (is_deleted = false);
   ```
2. **إضافة حقل `IPAddress` لنموذج التدقيق في Go (P1)**:
   إضافة `IPAddress string \`gorm:"column:ip_address"\`` في `models.AuditLog` وتعبئته من `c.IP()` في `logAudit`.

   استثناء الفواتير ذات `remaining_amount <= 0` من استعلام `tx.Where("customer_id = ? AND status IN ('Unpaid', 'Partially_Paid'))` لتجنب خطأ `chk_invoices_financials`.
4. **تحديث اختبار `db_verify_test.go` (P2)**:
