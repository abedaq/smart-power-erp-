## 2. سجل القواعد المحاسبية والمنطق المالي الحاكم (Business Logic Inventory)

يخضع النظام لمجموعة من المعادلات والقواعد المحاسبية الصارمة التي لا تقبل الخطأ أو التقريب غير المنضبط:

### 2.1 معادلات الاستهلاك والفوترة الأساسية
1. **قيمة الاستهلاك (Consumption)**:
   $$\text{Consumption} = \max(0, \text{CurrentReading} - \text{PreviousReading})$$
   - **قيد العداد غير التنازلي (Monotonic Reading Guard)**:
     - يُمنع منعاً باتاً تسجيل أي قراءة حالية تقل عن القراءة السابقة للعداد للمشترك النشط (`CurrentReading >= PreviousReading`).
     - يتم فرض هذا القيد في قاعدة البيانات (`CHECK constraint` وفي كود الـ Stored Procedure) وفي طبقة الخادم؛ وتُرفض القراءة المخالفة فوراً برسالة عربية واضحة: *"القراءة المدخلة أقل من القراءة السابقة المسجلة للعداد"*.
2. **تكلفة الوحدات المفقودة (Lost Units Cost)**:
   $$\text{LostUnitsCost} = \text{Round}(\text{LostUnits} \times \text{UnitPrice}, 2)$$
3. **إجمالي تكلفة الاستهلاك (Consumption Cost)**:
   $$\text{ConsumptionCost} = \text{Round}((\text{Consumption} + \text{LostUnits}) \times \text{UnitPrice}, 2)$$
4. **إجمالي المبلغ المستحق (Total Due)**:
   $$\text{TotalDue} = \text{Round}(\text{ConsumptionCost} + \text{FixedServiceFee} + \text{Arrears}, 2)$$
5. **المبلغ المتبقي (Remaining Amount)**:
   $$\text{RemainingAmount} = \max(0, \text{Round}(\text{TotalDue} - \text{PaidAmount}, 2))$$

### 2.2 الحالات المحاسبية للفواتير المعتمدة
- **مدفوعة بالكامل (`Paid`)**: عندما يكون $\text{RemainingAmount} \le 0$.
- **مدفوعة جزئياً (`Partially_Paid`)**: عندما يكون $\text{PaidAmount} > 0$ و $\text{RemainingAmount} > 0$.
- **غير مدفوعة (`Unpaid`)**: عندما يكون $\text{PaidAmount} = 0$.

### 2.3 التوزيع المائي للدفعات بالقفل المتشائم (FIFO Waterfall Payment Allocation)
عند توريد أي سند سداد لمشترك، يتم تطبيق خوارزمية التوزيع المائي المحاسبي داخل معاملة ذرية تضمن عدم التنافسية (Pessimistic Concurrency Control):
1. **قفل سجل المشترك**:
   ```sql
   SELECT id, balance FROM customers WHERE id = p_customer_id FOR UPDATE;
   ```
2. **استرجاع الفواتير غير المسددة مرتبة بالأقدم استحقاقاً مع قفل صفوفها**:
   ```sql
   SELECT id, total_amount, paid_amount, remaining_amount 
   FROM invoices 
   WHERE customer_id = p_customer_id AND status IN ('Unpaid', 'Partially_Paid')
   ORDER BY due_date ASC, id ASC 
   FOR UPDATE;
   ```
3. **توزيع مبلغ السداد بالتتابع المائي**:
   - لكل فاتورة مستحقة:
     $$\text{Allocation} = \min(\text{RemainingToDistribute}, \text{Invoice.RemainingAmount})$$
     $$\text{Invoice.PaidAmount} = \text{Invoice.PaidAmount} + \text{Allocation}$$
     $$\text{Invoice.RemainingAmount} = \text{Invoice.TotalAmount} - \text{Invoice.PaidAmount}$$
     $$\text{RemainingToDistribute} = \text{RemainingToDistribute} - \text{Allocation}$$
   - تقييد حركة التوزيع في جدول `payment_allocations`.
4. **معالجة الفائض (Overpayment)**:
   - إذا تبقّى مبلغ مالي بعد تسوية كافة الفواتير المستحقة ($\text{RemainingToDistribute} > 0$)، يتم قيد الفائض كرصيد دائن للمشترك في جدول `customer_credits` ليتم خصمه تلقائياً عند صدور أول فاتورة تالية.

### 2.4 الحساب التتابعي الرجعي للدورات (Retroactive Cascade Recalculation)
- عند تعديل قراءة عداد، أو رسوم، أو متأخرات في دورة سابقة $T$ عبر شبكة الإكسل التفاعلية:
  1. تبدأ معاملة ذرية (ACID Transaction) مع قفل كافة سجلات الفواتير والقراءات ذات الصلة.
  2. يُعاد احتساب الدورة $T$ بالقيم الجديدة.
  3. يتم ترحيل القراءة الحالية لـ $T$ لتصبح القراءة السابقة للدورة $T+1$.
  4. يتم ترحيل الرصيد المتبقي لـ $T$ ليصبح المتأخرات ($\text{Arrears}$) للدورة $T+1$.
  5. تتكرر عملية الاحتساب والترحيل تلقائياً وبشكل تتابعي حتى أحدث دورة $N$ مسجلة في النظام.
  6. يضمن هذا الإجراء انعدام أي انحراف في الأرصدة التراكمية وسجلات المديونية.

### 2.5 الترقيم المركب الحتمي للفواتير (Deterministic Invoice Numbering)
- يلتزم النظام بصيغة الترقيم المركب الموحدة:
  $$\mathbf{INV\text{-}[Cycle]\text{-}[SubscriberNumber]}$$
  - مثال: `INV-AUG1-10023` أو `INV-2026_08_1-10023`.
- يمنع هذا النمط تكرار الفواتير لنفس المشترك في نفس الدورة الفوترية، ويوفر مرجعية ثابتة لعمليات البحث والتدقيق وسندات القبض ومطبوعات الـ A5.

## 3. حصر وتوثيق واجهات الـ REST API (Complete 14 Groups / 54+ Endpoints)

يلتزم خادم Go Fiber بتقديم نفس عقود الـ JSON REST API الحالية تحت المسار الموحد `/api` على المنفذ `3000`:

### المجموعة 1: المصادقة (`/api/auth`)
1. `POST /api/auth/login`: تسجيل الدخول، التحقق من كلمة المرور المشفرة بـ BCrypt، إصدار JWT، وقيد الحدث في `audit_logs`.
2. `GET /api/auth/me`: جلب بيانات المستخدم الحالي وصلاحياته من الـ JWT Token.

### المجموعة 2: المستخدمين والتعيينات (`/api/users`)
3. `GET /api/users`: استعراض قائمة المستخدمين (خاص بـ `ADMIN`).
4. `POST /api/users`: إنشاء مستخدم جديد وتحديد دوره (`ADMIN`, `CASHIER`, `COLLECTOR`).
5. `PUT /api/users/:id`: تعديل بيانات المستخدم أو تجميد حسابه.
6. `POST /api/users/:id/reset-password`: إعادة تعيين كلمة مرور المستخدم.
7. `GET /api/users/assignments`: استعراض قائمة توزيع المشتركين على المحصلين.
8. `POST /api/users/assignments`: ربط مشترك بمحصل محدد.
9. `DELETE /api/users/assignments/:assignmentId`: حذف تعيين المشترك.

### المجموعة 3: المشتركين (`/api/customers`)
10. `GET /api/customers`: جلب قائمة المشتركين مع الفلاتر والصفحات وآخر قراءة وفاتورة.
11. `GET /api/customers/routes`: جلب قائمة أرقام خطوط السير الفريدة (`route_number`).
12. `GET /api/customers/regions`: جلب قائمة المناطق والعناوين الفريدة (`address`).
13. `GET /api/customers/:id`: جلب السجل الشامل للمشترك (فواتير، قراءات، سندات، أرصدة).
14. `POST /api/customers`: إنشاء مشترك جديد مع التحقق من عدم تكرار رقم المشترك أو العداد وقيد القراءة الابتدائية.
15. `PUT /api/customers/:id`: تعديل بيانات المشترك.
16. `PATCH /api/customers/:id/grid-cell`: تعديل خلية محددة في شبكة الإكسل وإطلاق الحساب التتابعي إن كانت مالية.
17. `DELETE /api/customers/:id`: حذف المشترك وسجلاته.

### المجموعة 4: القراءات وشبكة العمليات المباشرة (`/api/readings`)
18. `GET /api/readings/cycles`: استرجاع كافة دورات الفوترة مع مجاميع الاستهلاك والتحصيل والمتبقي.
19. `GET /api/readings/cycle-data`: جلب مصفوفة الـ 18 عموداً لدورة محددة مع حساب أيام التأخير ومجاميع الـ Footer.
20. `PUT /api/readings/:id/cell-update`: تعديل خلية القراءة، وإعادة الحساب التتابعي، وتحديث الفاتورة لحظياً.
21. `POST /api/readings/:id/approve-and-whatsapp`: اعتماد القراءة والفاتورة، وتوليد صورة الفاتورة وإدراجها بطابور الواتساب.
22. `POST /api/readings`: تسجيل قراءة جديدة عبر الإجراء المالي مع التحقق من تصاعد العداد والاعتماد التلقائي للمدير.
23. `GET /api/readings`: استعراض سجل القراءات المسجلة.
24. `POST /api/readings/approve-all`: اعتماد جماعي فوري لكافة القراءات المعلقة.
25. `POST /api/readings/approve/:id`: اعتماد قراءة فردية.
26. `POST /api/readings/reject/:id`: رفض قراءة مع تسجيل السبب وإلغاء الفاتورة المرتبطة.
27. `PUT /api/readings/:id`: تعديل قيمة القراءة وإعادة احتساب الفاتورة.

### المجموعة 5: التحصيل وسندات القبض (`/api/payments`)
28. `POST /api/payments`: تسجيل سند قبض جديد مع توليد رقم سند حتمي `REC-[Year]-[Seq]`، وتوزيع FIFO المائي.
29. `GET /api/payments`: استعراض قائمة سندات القبض والتوزيعات المحاسبية.
30. `POST /api/payments/approve/:id`: اعتماد سند القبض رسمياً وإشعار المشترك.
31. `POST /api/payments/reject/:id`: رفض السند وعكس كافة التوزيعات المحاسبية السابقة.
32. `PUT /api/payments/:id`: تعديل مبلغ السند وإعادة التوزيع المائي.
33. `POST /api/payments/:id/send-whatsapp`: توليد صورة سند القبض المعتمد وإدراجها بطابور الواتساب.

### المجموعة 6: الفواتير (`/api/invoices`)
34. `GET /api/invoices`: استعراض الفواتير مع تفاصيل القراءة والمشترك والمديونية.
35. `PUT /api/invoices/:id/pay`: سداد فاتورة فردية وتحديث حالتها.

### المجموعة 7: باقات الاشتراك (`/api/plans`)
36. `GET /api/plans`: جلب باقات الاشتراك وتعرفة الكيلوواط والرسوم الثابتة.
37. `POST /api/plans`: إضافة باقة اشتراك جديدة.
38. `PUT /api/plans/:id`: تعديل بيانات الباقة والتعرفة.
39. `DELETE /api/plans/:id`: حذف باقة اشتراك غير مرتبطة بمشتركين.

### المجموعة 8: التقارير والتحليلات الشاملة (`/api/analytics`)
40. `GET /api/analytics/monthly-performance`: مؤشرات الأداء المالي والتحصيل لآخر 6 أشهر.
41. `GET /api/analytics/overdue-report`: تقرير أعمار الديون والمشتركين المتعثرين (1-30, 31-60, 60+ يوم).
42. `GET /api/analytics/dashboard-summary`: ملخص كروت الـ KPIs وسجل العمليات الحية لمحصلي الميدان.
43. `GET /api/analytics/routes-progress`: نسبة إنجاز قراءة خطوط السير في الدورة الحالية.
44. `GET /api/analytics/unread-meters`: حصر العدادات المتأخرة عن القراءة لأكثر من X يوماً.
45. `GET /api/analytics/financial-summary`: الإيرادات، والتحصيل، والمتبقي مفصلة حسب الخطوط والدورات.
46. `GET /api/analytics/energy-loss`: تحليل فاقد الطاقة والوحدات المفقودة وتكلفتها المالية.
47. `GET /api/analytics/cycle-comparison`: مقارنة رقمية تفصيلية بين دورتين مختارتين.
48. `GET /api/analytics/collector-performance`: كشف أداء المحصلين وكفاءة القراءات والتحصيل.

### المجموعة 9: الواتساب ومحرك الرسائل (`/api/whatsapp`)
49. `GET /api/whatsapp/status`: حالة اتصال الواتساب وصورة رمز الاستجابة السريعة (QR Code Base64).
50. `POST /api/whatsapp/send-test`: إرسال رسالة تجريبية.
51. `POST /api/whatsapp/send-invoice`: إرسال صورة وبيانات فاتورة محددة عبر الواتساب.
52. `POST /api/whatsapp/send-warning`: إرسال إنذار فصل تيار لمشترك متعثر.

### 4.1 تفاصيل حزمة التقنيات (Tech Stack Details)
1. **خادم الويب**: Go Fiber v2 المبني على `fasthttp`، فائق السرعة، خفيف الموارد، وزمن استجابة يقارب 0ms للعمليات المحلية.
2. **برنامج التشغيل وقاعدة البيانات**: `github.com/jackc/pgx/v5` مع `gorm.io/gorm` و `gorm.io/driver/postgres`، متصل بـ `smartpower_db` محلياً عبر مجمع اتصالات (Connection Pool: Max 25 Open, 5 Idle).
3. **محرك الواتساب**: `go.mau.fi/whatsmeow` مع مخزن الجلسات في PostgreSQL (`whatsmeow/store/sqlstore`) ومترجم بـ `CGO_ENABLED=0` بدون Cgo.
4. **توليد الفواتير A5**: `github.com/chromedp/chromedp` للتواصل مع متصفح Edge المحلي وتوليد صور وملفات A5 فائقة الدقة بتشكيل عربي سليم 100%.
5. **معالجة الإكسل**: `github.com/xuri/excelize/v2` للتصدير والاستيراد الدافق (Streaming) باستهلاك ذاكرة < 20MB.
6. **الواجهة الأمامية**: React 19 + TypeScript + Vite + Tailwind CSS، مبنية بـ `base: './'` ومدمجة عبر `//go:embed` داخل الخادم.
7. **النسخ الاحتياطي والتعافي**: جدولة يومية آلية لـ `pg_dump -Fc` مع فحص أقراص الـ USB عبر Win32 API (`GetDriveTypeW`) والتحقق من تجزئة SHA-256.
